# Matawaka Workbench

Independent Windows workbench for bounded analysis and development flows over the local Matawaka catalog.

## v0.5 checkpoint

```text
JSON command
  -> terminal-safe router
  -> catalog snapshot (repo + branch + HEAD)
  -> typed read-only capability decision
  -> balanced evidence frontier
  -> offline provider selection
  -> sanitized evidence packet
  -> verify fixed SemanticHost SHA-256 against build manifest
  -> start fixed SemanticHost process
  -> assign Windows Job Object before semantic input
  -> stdin JSON / stdout typed receipt
  -> parent digest verification
  -> typed semantic/process boundary receipts
  -> proposal/checkpoint
  -> STOP before materialization or mutation
```

The Windows UI exposes Events, Result, Evidence Receipt, Authority Receipt, Liveness, Semantic Provider, Process Boundary and Agent tabs.

### Windows bounded child-process boundary

v0.5 keeps the v0.4 separate-process IPC boundary and adds two independent controls before semantic data is written to the child:

1. the published `Matawaka.Workbench.SemanticHost.exe` SHA-256 must match `semantic-host.integrity.json` generated by the accepted build;
2. the fixed host process must be assigned to a fresh Windows Job Object with:
   - `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`;
   - active-process limit `1`;
   - per-process committed-memory limit `256 MiB`;
   - no breakaway flags enabled.

The Job Object is applied after the trusted fixed process starts but **before the semantic stdin packet is written**. If integrity verification or Job Object assignment fails, semantic input is not sent and the run fails closed.

Provider ids remain a closed built-in registry:

- `local-contract-synthesis-v0.3`;
- `deterministic-evidence-semantic-v0.2`.

The child receives one sanitized JSON packet over stdin and returns one JSON receipt over stdout. JSON cannot provide an executable path, DLL, script or dynamic assembly path.

The child environment is rebuilt from an explicit allowlist and uses an isolated temporary working directory. Parent-side code enforces timeout, cancellation, input/output size limits, provider identity, input digest and output digest verification.

### Honest isolation boundary

The child still uses the same Windows user token as Workbench. v0.5 does **not** create a restricted token, AppContainer, filesystem ACL sandbox, VM or network sandbox. Job Objects provide process/resource containment; they do not remove all same-user OS capabilities.

`Process Isolation != OS Sandbox`

`Job Object Containment != Restricted Token`

`Resource Limit != Authority Grant`

`Offline Provider Implementation != Network Sandbox`

`Binary Integrity != Provider Authority`

The shipped host/providers are fixed local code and perform no network model calls or repository mutation, but v0.5 does not claim that arbitrary hostile same-user code would be unable to access the filesystem or network.

### Authority

`freeshield-read-only-bridge/v0.5` grants only read-only Observe/Propose when explicitly enabled and when requested mutation/network/arbitrary-process authority remains zero/false. The trusted fixed semantic-host launch and Job Object containment are internal implementation steps and are not exposed as arbitrary-process authority to JSON or providers.

Execute remains denied before evidence collection and before semantic process launch.

## Repository line endings

v0.5 adds `.gitattributes` so textual repository content is normalized to LF, while PowerShell/solution launcher surfaces use CRLF where declared. This makes line-ending policy repository-visible instead of relying only on local Git configuration.

## Local layout

Workspace: `K:\Matawaka`

Catalog: `K:\Matawaka\Catalog`

The Workbench has a local accepted Git predecessor chain. Catalog repositories are evidence sources and are not modified by the v0.5 patch.
